# Formato do MISSION.md

`MISSION.md` vive na raiz do workspace. Captura a _razão_ pela qual o dev está aprendendo este tema. Toda decisão de ensino (o que ensinar a seguir, quais recursos trazer à tona, quais exercícios desenhar) deve remontar a este documento.

## Template

```md
# Missão: {Tema}

## Por quê
{1-3 frases. O objetivo concreto do mundo real que o dev está buscando. O que muda na vida ou no trabalho dele quando ele tiver essa skill? Evite enquadramentos abstratos como "para entender X"; busque o resultado subjacente.}

## Sucesso parece com
- {Uma coisa específica e observável que o dev vai conseguir fazer}
- {Outra coisa específica}
- {…}

## Restrições
- {Tempo, orçamento, compromissos prévios, preferências de aprendizado, qualquer coisa que limite a abordagem}

## Fora de escopo
- {Tópicos adjacentes que o dev explicitamente não quer perseguir agora, protegendo a zona de desenvolvimento proximal}
```

## Regras

- **Uma missão por workspace.** Se o dev quer aprender duas coisas não relacionadas, isso é dois workspaces.
- **Concreto acima de abstrato.** "Correr uma meia maratona até outubro" vence "ficar mais em forma". "Lançar uma CLI em Rust para o time" vence "aprender Rust".
- **Confronte a vagueza.** Se o dev não consegue articular o porquê, entreviste-o antes de escrever qualquer coisa. Uma missão ruim é pior que nenhuma missão.
- **Revise quando a realidade muda.** Missões mudam. Quando o objetivo do dev se move, atualize este arquivo: não deixe uma missão obsoleta guiando sessões futuras.
- **Mantenha curto.** Se `MISSION.md` passar de uma tela, ele parou de ser uma bússola e virou um plano.
